# PRD 撰写常用术语表

本文档定义 prd-writer 在起草 PRD 时使用的核心术语，避免歧义。

---

## 文档体系

| 术语 | 定义 |
|---|---|
| **PRD**（Product Requirements Document）| 产品需求文档。**业务契约层**：描述"做什么、为什么、做到哪里"。本 skill 的产出 |
| **FS**（Functional Spec / Specification）| 功能规格书。**实现契约层**：描述"怎么做"，含字段、表结构、API、状态机。由 prd-writer 的下游 skill `fs-writer` 派生 |
| **US**（User Story）| 用户故事。如有需要可由 PRD 的 FR 进一步派生（本 skill 默认不输出） |
| **Test Case**（测试用例）| 测试场景。可由 PRD 的"验收标准"或 FS 的"功能逻辑"派生 |

---

## 需求层级

| 术语 | 定义 |
|---|---|
| **模块**（Module）| 系统的一级划分，如"报价模块"、"寻源模块"。**一个模块对应一份 PRD** |
| **能力组**（Capability Group）| 模块内的二级分组，按业务阶段或对象聚类（如"模板配置 / 供应商响应 / 报价分析"）|
| **功能点 / FR**（Functional Requirement）| 模块内最小可独立交付的功能单元。一个 FR-NNN 对应一份 FS（或合并为一组 FS）|
| **业务规则 / BR**（Business Rule）| FR 内的具体规则项。本 skill 用 1./2./3. 编号列出，不单独编号 BR |

---

## 优先级

| 标记 | 含义 |
|---|---|
| **P0** | 本期必须实现；缺失即 PRD 不完整 |
| **P1** | 本期推荐实现；可暂缓但需在本期版本规划内 |
| **P2** | 设计意图保留，本期不实现；FS 仅需 schema 预留扩展位 |

**经验法则**：所有 FR 都 P0 = 没优先级。要求 P0 占比 ≤ 70%。

---

## 撰写阶段

| 术语 | 定义 |
|---|---|
| **Step 0 输入识别** | 读取 RFP / 客户邮件 / 调研笔记，识别本次 PRD 覆盖范围 |
| **Step 1 P0/P1 澄清** | 一批问题，P0 必答、P1 带默认值，限 8 个以内 |
| **Step 2 v0.1 业务意图** | 起草 §1~§4（摘要、上下文、流程、实体）|
| **Step 3 v1.0 完整版** | 起草 §5~§6（功能点、范围）|
| **Step 4 可选章节** | 询问是否追加 §7 OQ / §8 备注 |

---

## 编号约定

| ID | 格式 | 用途 |
|---|---|---|
| FR-NNN | FR-001, FR-002... | 功能点编号，3 位数前补零，PRD 跨版本稳定不复用 |
| OQ-NNN | OQ-001... | 待决问题编号（§7 可选）|

**不使用**的编号体系（旧版 prd-writer 用过，新版砍掉）：
- ❌ NFR-NNN（非功能需求独立编号）
- ❌ BR-NNN-NN（业务规则二级编号）
- ❌ A-NNN（假设独立编号）
- ❌ DEP-NNN（依赖独立编号）
- ❌ D-NNN（决策日志编号）

---

## 边界术语

| 术语 | 边界 |
|---|---|
| **业务实体** | PRD §4 描述实体的**业务概念**，不写字段。例："报价模板：定义供应商应当如何填报价；有生命周期" |
| **字段** | 字段定义、类型、长度、必填等都归 FS §6 数据表结构 |
| **业务流程** | PRD §3 用 Mermaid flowchart 表达；节点为业务动作，不写系统组件（前端/API/DB）|
| **状态机** | PRD 可在业务规则里简略描述（"状态：草稿→已发布→已停用，单向不可逆"）；详细状态机由 FS 承载 |

---

## 角色术语

| 角色 | 描述 |
|---|---|
| **业务方** | 客户的业务部门负责人，是 PRD 的最终签字方 |
| **PM** | 产品经理；是 prd-writer 的主要使用者 |
| **业务顾问** | 客户方业务专家，配合 PM 提供细节 |
| **下游 FS 起草者** | 接收 PRD 后起草 FS 的人；PRD 末尾可附"给 FS 起草者的提示"指引他们 |
