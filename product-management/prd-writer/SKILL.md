# prd-writer

把模糊的业务需求翻译成结构化、可下传 FS 的 PRD。**PRD 是业务契约**（讲清"做什么、为什么、做到哪里"），**不是技术规格**（字段、表、API 都留给 FS）。

## PRD 与 FS 的协作

```
PRD（一份 = 一个模块）
  ├── 业务流程 + 业务实体 → 识别功能点
  └── 功能点列表（FR-NNN）
       ↓
       fs-writer 派生 FS（一份功能点 = 一份 FS）
```

**关键纪律**：PRD 不写字段、不写表结构、不写 API。这些归 FS。PRD 只描述业务实体（"模板"、"订单"）与它们之间的关系，不描述实体的字段。

## PRD 8 节模板（核心 6 + 可选 2）

| 节 | 内容 | 必选 |
|---|---|---|
| 1. 摘要 | 1-2 段：业务背景、目标、核心价值 | ✅ |
| 2. 业务上下文 | 问题陈述、目标用户、为什么是现在 | ✅ |
| 3. 业务流程 | 端到端业务流程（Mermaid flowchart），多流程则多图 | ✅ |
| 4. 业务实体 | 关键业务实体与关系（不写字段；ER 图可选）| ✅ |
| 5. 功能点列表 | FR-NNN 列表，按"能力组"分组 | ✅ |
| 6. 范围 | 范围内 / 范围外 / 未来扩展 | ✅ |
| 7. 待决问题 | OQ-NNN 列表（默认不写） | 🟡 可选 |
| 8. 备注 | 关键约束、依赖、假设（默认不写） | 🟡 可选 |

## FR 的 6 字段格式

```
### FR-NNN <祈使句标题>
- **优先级**：P0 / P1 / P2
- **用户角色**：<谁触发或受益>
- **业务规则**：
  1. <规则 1>
  2. <规则 2>
- **验收标准**：
  - 给定 X，当 Y 时，则 Z
- **依赖/备注**：<可选；引用其他 FR 或外部模块>
```

**禁止字段**：
- ❌ 触发条件、输入、输出 → 留给 FS §5 功能逻辑
- ❌ 边界情况、错误码 → 留给 FS
- ❌ FS 钩子、US 钩子 → 不需要正式钩子；FR 标题与业务规则就是钩子
- ❌ 关联流程编号、原型编号 → 让读者自己在 PRD 内导航

## 工作流（分段渐进式）

**核心原则：每节写完邀请用户确认或调整，不要一次写完全部。**

### Step 0 — 输入识别（30 秒内）

1. 读用户提供的输入（RFP / 客户邮件 / 现有系统文档 / 调研笔记）
2. 用一句话回应"本次 PRD 覆盖：<模块名>，主要面向<用户角色>"
3. 等用户确认或修正

如果没有任何输入，问用户：要写的是什么模块？解决什么业务问题？

### Step 1 — P0/P1 澄清（一批问题，限 8 个）

使用 `AskUserQuestion` 一次性问完关键问题，**带 P0/P1 标签**：

- **P0**：必答，不答无法起草；通常是范围、用户角色、关键边界
- **P1**：带默认值，不答按默认推进

格式示例：

```
🔴 P0 — 必答（阻塞起草）
1. <问题> — 选项 A / B / C
2. <问题> — 选项 A / B

🟡 P1 — 可推进（不答按默认）
3. <问题> — 默认：<X>
4. <问题> — 默认：<Y>
```

**澄清原则**：
- P0 限 5 个以内，P1 限 5 个以内，总数 ≤ 8 个
- P0 必须能在 30 秒内回答；过长则拆
- P1 必须有具名默认值；没默认就降级为 P0
- 必含一题**范围排除追问**（"什么不做？"通常比"什么要做？"更能避免范围蔓延）

### Step 2 — 起草 v0.1 业务意图（§1 ~ §4）

按顺序写：

1. **§1 摘要** — 1-2 段，含业务背景、目标、核心价值。不超过 8 行
2. **§2 业务上下文** — 三件事：问题陈述（当前痛点）、目标用户（角色描述）、为什么是现在（驱动因素）
3. **§3 业务流程** — 用 Mermaid flowchart 画核心业务流程。多流程则多图。**不画系统组件**（如前端/API/DB），只画业务动作与决策点
4. **§4 业务实体** — 列实体清单（名称 + 一句话）+ ER 图（实体间关系，不写字段）

写完邀请用户审阅。

### Step 3 — 起草 v1.0 完整版（§5 ~ §6）

5. **§5 功能点列表** — FR-NNN 按"能力组"分组（如"能力组 A：模板配置"、"能力组 B：响应处理"）。每条 FR 用 6 字段格式
6. **§6 范围** — 三块：范围内（含 P0/P1）、范围外（含排除原因）、未来扩展

写完邀请用户审阅。

### Step 4 — 询问是否追加可选章节

```yaml
question: "PRD 主体（§1~§6）已完成。是否追加可选章节？"
options:
  - "都不追加（推荐）— PRD 在 §6 结束，可下传 fs-writer"
  - "追加 §7 待决问题（OQ-NNN）"
  - "追加 §8 备注（约束/依赖/假设）"
```

默认推荐"都不追加"。多数项目到 §6 已足够给 fs-writer 用。

## 写作要求

- **短而精**：每节用最少篇幅讲清楚；不写"设计决策记录""为什么这样设计"等元说明
- **业务语言**：用"模板"、"订单"，不用 `quotation_template`、`sales_order`
- **不写字段**：PRD §4 业务实体只描述实体（"报价模板"），不列字段（"模板名称 VARCHAR(200)"）—— 字段是 FS 的事
- **业务规则要明确**：每条业务规则一句完整中文句，含条件与结果（如"模板名称在租户内不可重复，重名时拒绝创建并提示用户改名"）
- **验收标准用 Given-When-Then**：让 QA 能直接派生测试用例
- **优先级要克制**：能 P1 不 P0，能 P2 不 P1。所有 FR 都 P0 = 没优先级

## 常见错误（自检清单）

| 错误 | 问题 | 正确做法 |
|---|---|---|
| §4 业务实体里列字段 | PRD 与 FS 边界混乱 | 只描述实体名 + 一句话，字段留给 FS |
| FR 业务规则写成 SQL 或代码 | 业务方看不懂 | 用完整中文句，含条件与结果 |
| 没有"范围外"小节 | 范围蔓延风险高 | §6 必含"范围外"，列 5+ 项排除并写排除原因 |
| 一上来就写 v1.0 | 方向错了返工大 | 必走 v0.1 业务意图 → 用户确认 → v1.0 |
| FR 全部 P0 | 实质上没优先级 | 强制分级，至少 30% 不能是 P0 |
| 跳过澄清直接起草 | 起草内容偏离客户真实意图 | Step 1 至少问 3 个 P0 问题 |

## 不写什么

- **不写字段级 schema** — PRD §4 业务实体不列字段；字段留给 FS §6
- **不写 API 路径 / HTTP method** — 留给 FS §8（如有需要）
- **不写错误码** — 错误**提示文案**可在 FR 业务规则里写完整中文句；错误码编号留给 FS
- **不写性能指标具体数字**（如 "P95 < 500ms"）— 若必须，放 §8 备注；通常留给 FS NFR
- **不写技术选型**（PostgreSQL / Redis 等）— 任何具体选型都属于技术设计层
- **不写界面原型 / ASCII 线框** — 界面留给 FS §3；PRD 仅描述"用户能在工作台筛选并查询"这类业务能力

## 修订模式

目标 PRD 已存在时，问用户：

1. 改某节内容（指定节号）
2. 加新功能点（追加 FR-NNN）
3. 范围调整（增删 §6 内某项）
4. 整体重写（v1.0 → v2.0）

修订后在文件末尾追加 CHANGELOG。

## 与 fs-writer 的衔接

PRD 写完后，下游 fs-writer 的输入是：

1. **§5 功能点列表**：每个 FR-NNN 派生一份 FS（或一组相关 FR 合并为一份 FS）
2. **§3 业务流程**：FS §1 流程说明的输入
3. **§4 业务实体**：FS §6 数据表结构的输入（FS 才落字段）
4. **§6 范围**：fs-writer 用来判断 FS 是否在范围内

**给 fs-writer 的友好提示**：在 PRD 末尾可加一段"### 给 FS 起草者的提示"：
- 哪几个 FR 建议合并为一份 FS（如紧耦合的）
- 哪几个 FR 必须独立成 FS（如有独立状态机的）
- 哪些 P2 FR 仅需 schema 预留（未来实现）
