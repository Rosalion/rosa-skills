# prd-writer

把模糊的业务需求翻译成结构化、可下传 FS 的 PRD。**PRD 是业务契约**（讲清"做什么、为什么、做到哪里"），**不是技术规格**（字段、表、API 留给 FS）。

## 起草前必读

每次起草前**必须**先读 `memory/lessons.md`，让历史教训指导本次撰写。

## PRD 与 FS 的协作

```
PRD（一份 = 一个模块）
  ├── 业务流程 + 业务实体 → 识别功能点
  └── 功能点列表（FR-NNN）
       ↓
       fs-writer 派生 FS（一份功能点 = 一份 FS）
```

**关键纪律**：PRD 不写字段、不写表结构、不写 API。这些归 FS。

## PRD 8 节模板

| 节 | 内容 | 必选 |
|---|---|---|
| 1. 摘要 | 1-2 段：业务背景、目标、核心价值 | ✅ |
| 2. 业务上下文 | 问题陈述、目标用户、为什么是现在 | ✅ |
| 3. 业务流程 | 端到端业务流程（Mermaid flowchart），多流程则多图 | ✅ |
| 4. 业务实体 | 关键业务实体与关系（不写字段；ER 图可选）| ✅ |
| 5. 功能点列表 | FR-NNN 列表，按"能力组"分组 | ✅ |
| 6. 范围 | 范围内 / 范围外 / 未来扩展 | ✅ |
| 7. 待决问题 | OQ-NNN 列表（默认不写） | 🟡 可选 |
| 8. 备注 | 关键约束、依赖、假设（默认不写） | 🟡 可选 |

## FR 的 6 字段格式

```
### FR-NNN <祈使句标题>
- **优先级**：P0 / P1 / P2
- **用户角色**：<谁触发或受益>
- **业务规则**：
  1. <规则 1>
  2. <规则 2>
- **验收标准**：
  - 给定 X，当 Y 时，则 Z
- **依赖/备注**：<可选>
```

**禁止字段**：触发条件、输入、输出、边界情况、错误码、FS 钩子、US 钩子、关联流程编号、关联原型编号。这些信息留给 FS。

## 工作流（分段渐进式）

每节写完邀请用户确认或调整，不要一次写完全部。

### Step 0 — 输入识别（30 秒内）

1. 读用户提供的输入（RFP / 客户邮件 / 现有系统文档 / 调研笔记）
2. 用一句话回应"本次 PRD 覆盖：<模块名>，主要面向<用户角色>"
3. 等用户确认或修正

如果没有任何输入，问用户：要写的是什么模块？解决什么业务问题？

### Step 1 — P0/P1 澄清（一批问题，限 8 个）

使用 `AskUserQuestion` 一次性问完关键问题，**带 P0/P1 标签**：

- **P0**：必答，不答无法起草；通常是范围、用户角色、关键边界
- **P1**：带默认值，不答按默认推进

**澄清原则**：
- P0 限 5 个以内，P1 限 5 个以内，总数 ≤ 8 个
- P0 必须能在 30 秒内回答；过长则拆
- P1 必须有具名默认值；没默认就降级为 P0
- **必含一题范围排除追问**（"什么不做？"通常比"什么要做？"更能避免范围蔓延）

复杂场景遇到"问什么不知道"或"用户回答太泛"时，读 `reference/clarification-patterns.md`。

### Step 2 — 起草 v0.1 业务意图（§1 ~ §4）

按顺序写：

1. **§1 摘要** — 1-2 段，含业务背景、目标、核心价值。不超过 8 行
2. **§2 业务上下文** — 问题陈述（当前痛点）、目标用户（角色描述）、为什么是现在
3. **§3 业务流程** — 用 Mermaid flowchart 画核心业务流程。多流程则多图。**不画系统组件**（前端/API/DB），只画业务动作与决策点
4. **§4 业务实体** — 列实体清单（名称 + 一句话）+ ER 图（实体间关系，不写字段）

写完邀请用户审阅。

### Step 3 — 起草 v1.0 完整版（§5 ~ §6）

5. **§5 功能点列表** — FR-NNN 按"能力组"分组。每条 FR 用 6 字段格式
6. **§6 范围** — 三块：范围内（含 P0/P1）、范围外（含排除原因，至少 5 项）、未来扩展

写完邀请用户审阅。

### Step 4 — 询问是否追加可选章节

询问用户是否追加 §7 待决问题 / §8 备注。默认推荐都不追加；多数项目到 §6 已足够给 fs-writer 用。

## 与 fs-writer 的衔接

PRD 写完后，下游 fs-writer 的输入是：

- **§5 功能点列表**：每个 FR-NNN 派生一份 FS（或一组相关 FR 合并）
- **§3 业务流程**：FS §1 流程说明的输入
- **§4 业务实体**：FS §6 数据表结构的输入（FS 才落字段）
- **§6 范围**：fs-writer 用来判断 FS 是否在范围内

**给 fs-writer 的友好提示**：在 PRD 末尾可加一段"### 给 FS 起草者的提示"：
- 哪几个 FR 建议合并为一份 FS
- 哪几个 FR 必须独立成 FS（如有独立状态机的）
- 哪些 P2 FR 仅需 schema 预留

## 修订模式

目标 PRD 已存在时，问用户：

1. 改某节内容（指定节号）
2. 加新功能点（追加 FR-NNN）
3. 范围调整（增删 §6 内某项）
4. 整体重写（v1.0 → v2.0）

修订后在文件末尾追加 CHANGELOG。**重要修订经验请记录到 `memory/lessons.md`**。
