## 常见错误自检（每次起草前过一遍）

| 错误 | 问题表现 | 正确做法 |
|---|---|---|
| §4 业务实体里列字段 | 写出 "模板名称 VARCHAR(200)" 这类技术细节 | 只描述实体名 + 业务概念，字段留给 FS §6 |
| FR 业务规则写成 SQL 或代码 | "UPDATE status='Deprecated'" | 用完整中文句：将状态改为"已停用" |
| 没有"范围外"小节 | §6 只有范围内，缺范围外 | §6 必含"范围外"，列 5+ 项排除并写原因 |
| 一上来就写 v1.0 | 跳过 v0.1 业务意图直接全文 | 必走 v0.1 → 用户确认 → v1.0 |
| FR 全部 P0 | 优先级汇总 P0 = 100% | 强制分级，至少 30% 不能是 P0 |
| 跳过 Step 1 澄清直接起草 | 起草内容偏离客户真实意图 | Step 1 至少问 3 个 P0 问题 |
| 用户回答太泛就直接采纳 | "默认按业内惯例" 这种回答被沿用 | 追问到具体可执行的值；否则降级为 OQ |
| §3 业务流程画系统组件 | 流程图里出现 "前端 → API → DB" | 流程图只画业务动作 + 决策点 |
| FR 字段超过 6 个 | 多写了 "输入/输出/边界情况" 等 | 严格 6 字段：标题/优先级/用户角色/业务规则/验收标准/依赖备注 |
| OQ 没有负责人或截止日期 | OQ-001 仅有问题描述 | 必含负责人 + 截止日期；否则 OQ 等于不存在 |

## 高价值机制（来自实战的提炼）

### 1. P0/P1 澄清的"30 秒原则"

**P0 题必须能在 30 秒内回答**。如果一题用户需要思考超过 30 秒，那说明：
- 问题本身需要拆分
- 或者用户内部还没达成一致 → 应该降级为 OQ

### 2. 范围排除追问的"清单式"

不要开放性问 "你不想做什么"。**列 7~10 项让用户逐项标注 "做/不做"**。开放性问题用户会回答"不知道"；清单式逼用户做判断。

### 3. P2 设计意图保留的价值

发现某 FR 本期不做但未来可能做，**不要直接砍掉**，而是标 P2 保留：
- 锁定未来语义边界（避免后续重新讨论）
- 让下游 FS 预留 schema 扩展位
- 减少未来"做不做、做到哪"的扯皮

### 4. "给 FS 起草者的提示" 的价值

PRD 末尾附一段建议 FS 拆分方案的提示，让下游不再重新做拆分判断。这是 PRD → FS 衔接的关键。

## 反复出现的疑问与统一答复

### Q1：PRD 要不要写 NFR（性能、安全、可用性）？

**A**：本 skill **不为 NFR 单独立节**。必要时放进 §8 备注（如"P95 < 500ms 是基础设施约束"）。
- 多数 NFR 应留给 FS §10 NFR
- PRD 不写 NFR 的具体数字（如 "P95 < 500ms"）；只在 §8 备注约束性的业务底线

### Q2：PRD 要不要写界面原型？

**A**：**不写**。界面原型留给 FS §3 功能界面（ASCII 原型）。PRD §3 业务流程只用 Mermaid 表达业务动作。

### Q3：FR 太多怎么办（>30 个）？

**A**：检查是不是模块拆得太大。一个 PRD 一个模块；如果 FR > 30，可能需要拆成两个模块两份 PRD。

### Q4：业务方说"先大致写一下，细节后面再补"？

**A**：必须 Step 1 至少问 3 个 P0 题。完全跳过澄清直接起草的 PRD 几乎必返工。
