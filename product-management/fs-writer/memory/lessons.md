**范围界定**：

- ❌ 不适合放入：版本号修订日志（属于 CHANGELOG）、一次性任务的备忘（属于待办或开发笔记）

## 常见错误自检（每次起草前过一遍）

| 错误 | 问题表现 | 正确做法 |
|---|---|---|
| 业务规则写成 SQL/赋值 | "标准业务规则"列写 `quotation_template.status = 'Deprecated'`、`status='Draft'`、`UPDATE ... WHERE ...` | 用完整中文句：将模板状态由"已发布"改为"已停用" |
| 把数据库列名当业务术语 | "标准业务规则"列直接出现 `is_hidden`、`effective_from`、`ref_count` | 中文为主，必要时括号附带英文（如"启用日期（effective_from）"）|
| 枚举值写在取值逻辑列 | "取值逻辑：选择，01-销售订单 / 02-交货" | 枚举值独立成表；取值逻辑写"参考【XX 配置表】"|
| 多个按钮操作混一段 | 一个"详细功能逻辑"段落同时写"新增/修改/删除/审批" | 每个按钮独立一段，标注触发按钮名称 |
| 抽象触发词 | "触发：用户触发"、"触发：流程触发" | 必标四类之一：用户操作（具体按钮名）/ 系统自动 / 被调用 / 定时任务 |
| 定时任务漏掉 | §5 全是用户操作动作，没看见定时任务 | 自查：是否有过期清理、缓存刷新、状态扫描等定时任务？|
| 字段类型用 SQL 方言 | VARCHAR(200)、BIGINT(20)、DECIMAL(10,2) | 用业务类型：CHAR、NUM、DATE、DATETIME、ACL、勾选框、JSON |
| 字段名只有英文或只有中文 | "字段：status / VARCHAR / 20 / 状态" | 中英双写：字段名（中文）+ 字段ID（英文）独立两列 |
| §4 §6 不一致 | §4 字段说明里用 CHAR、§6 数据表用 VARCHAR | 两节统一用业务类型 |
| §3 界面没 ASCII 原型 | 界面只用文字列举元素 | 默认每个界面块含 1 张 ASCII 原型 |
| §5 全部用步骤表（复杂动作硬塞步骤）| 含 4+ 条件分支硬写成步骤表 1/2/3/4 | 复杂动作追加决策表 / 分支流程图 / 异常清单（详见 `reference/complex-logic.md`）|
| 表单类型不标注 | §6 表名上方没标"新增配置表" 还是 "已有表加字段" | 必标四种之一：新增配置表 / 新增枚举表 / 新增子表单 / 已有表单加字段 |
| §3 §4 §6 不标归属模块 | 章节内只有表名，没说所属模块 | 章节顶部标"所属模块：XX - YY" |
| FS 复制 PRD 大段业务背景 | §1 摘要重复 PRD §2 业务上下文 | 仅引用 PRD，不重复；FS 重点写"怎么做" |
| 公式字段忘记预留扩展位 | §6 schema 没含 P2 FR 需要的 formula 字段位 | 检查 PRD 是否有 P2 FR；若有则 schema 必须预留对应字段位 |

## 标准业务规则列写作规范（强制）

| 维度 | 要求 | ❌ 错误 | ✅ 正确 |
|---|---|---|---|
| 句子完整性 | 完整中文句（有主谓宾）| `status = 'Deprecated'` | 将模板状态改为"已停用" |
| 词汇 | 中文业务术语为主 | `effective_from` | 启用日期 |
| 枚举值 | 用业务值 | `'Published'` | "已发布" |
| 必要英文 | 必要时括号附带 | 全中文导致字段歧义 | 将启用日期（effective_from）设为... |
| 表达 | 写因果与约束 | "状态改为已停用" | 将状态由"已发布"改为"已停用"；此操作不可逆 |
| 字段更新 | 用动词描述 | `占用金额 += 金额` | 将业务伙伴信用视图的"未清销售订单占用"金额累加上本订单金额 |
| 错误提示 | 原文照搬 | "提示错误" | 提示"模板名称已存在，请改用其他名称" |

## 高价值机制（来自实战的提炼）

### 1. 一份 FS = 一个或一组紧密相关的功能点

5~10 个 FR 拆 1 份 FS 比较合理。20+ FR 一份 FS 太厚；1 FR 一份 FS 太碎。

判断是否独立成 FS：是否有**独立的状态机**？是否有**独立的 API 子域**？是否是 **P2 FR**（可在主 FS 中预留即可）？

### 2. 分段渐进式（Step 1 → Step 2 → Step 3）

Step 1（§1~§3 流程界面）写完邀请用户审阅，再写 Step 2。避免一次写完用户全否定。

### 3. 复杂逻辑的 4 种表达手段

简单 CRUD 用步骤表即可。复杂动作按需追加：决策表（多分支）、分支流程图（异常路径）、异常清单（完整覆盖）、算法说明（循环/重试）。详见 `reference/complex-logic.md`。

### 4. P2 FR 的 schema 预留

PRD 中标注 P2 的 FR（本期不实现），FS §6 数据表必须**预留对应字段位**（如 formula、is_anomaly），本期为 NULL，未来上线时无需破坏性迁移。

### 5. ASCII 原型作为开发对齐工具

§3 功能界面默认含 ASCII 原型。这是给前端开发"对齐布局意图"的最低成本工具。前端实施前可与设计师对照 ASCII 找差异。

## 反复出现的疑问与统一答复

### Q1：FS 要不要写 API（HTTP 路径、JSON Schema、错误码）？

**A**：默认不写。Step 3 用户主动追加 §7 API 设计才写。理由：现代前后端一体化（monorepo / 类型共享）项目，API 已自动派生；只有跨服务、对外开放 API 才需要正式 HTTP 契约。

### Q2：FS 要不要写测试用例？

**A**：默认不写。Step 3 用户主动追加 §8 测试用例才写。理由：测试用例通常由专门的测试用例库承载；FS §5 步骤表已是测试用例的良好骨架。

### Q3：状态机要不要独立成章？

**A**：**不独立**。状态值在 §4 关键字段说明的取值逻辑列或独立枚举表；状态流转规则在 §5 功能逻辑的对应动作中描述。强行独立成章会让 FS 在"状态-动作"间来回跳，难读。

### Q4：FR 跨模块怎么处理？

**A**：FS 是本模块视角。跨模块部分用"引用其他 FS"表达（如"调用 FS_SRM_M005 的影响摘要接口获取数据"）。跨模块的具体实现归对方 FS。

### Q5：错误码独立成章吗？

**A**：默认嵌在 §5 步骤表的"标准业务规则"列里（如"提示用户：模板名称已存在"）。仅在 Step 3 用户追加 §7 API 时才单独整理错误码表。
