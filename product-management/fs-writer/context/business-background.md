# FS 撰写的业务背景

帮助 fs-writer 理解开发交付场景。仅在用户提供的 PRD 不足时按需引用。

---

## FS 的读者与目的

FS 主要给三类人看：

| 读者 | 关心的章节 | 关心的形式 |
|---|---|---|
| **后端开发** | §6 数据表结构、§5 功能逻辑 | 字段精确、SQL 业务语义清晰 |
| **前端开发** | §3 功能界面、§4 关键字段说明 | ASCII 原型、字段配置 |
| **QA / 测试** | §5 功能逻辑、§4 字段说明 | 步骤表 + 决策表（可派生测试用例）|

**FS 的目的**：让以上三类人**无歧义地理解业务**并按此实施。文档既要业务可读（PM、业务方能审阅），又要技术精确（开发能照抄实现）。

---

## 现代化前后端一体化开发

很多项目走 monorepo / 类型共享：
- 前端通过 hooks / actions / stores 调后端，**不再依赖独立 HTTP API 契约**
- 字段类型靠 TypeScript / Schema 自动共享

这种项目 **§7 API 设计默认不写**，仅在跨服务对接、对外开放 API 时才写。

传统跨团队 / 跨技术栈项目则仍需要 §7 API 设计明确 HTTP 契约。Step 3 询问用户是否追加 §7。

## FS 与 PRD 的边界

| 内容 | PRD | FS |
|---|---|---|
| 业务背景 | ✅ §2 业务上下文 | 仅引用，不重复 |
| 业务流程 | ✅ §3 业务流程 | 在 §1 流程说明中具化（增加界面交互细节）|
| 业务实体 | ✅ §4 业务实体（概念层）| ❌ 不重复；字段在 §6 数据表结构 |
| 字段级 schema | ❌ 不写 | ✅ §6 数据表结构 |
| 功能点 | ✅ §5 FR-NNN | 由此派生本 FS |
| 业务规则实现 | 业务语言描述 | ✅ §5 功能逻辑（步骤表 + 触发类型）|
| 界面原型 | ❌ 不画 | ✅ §3 功能界面 |
| 状态机 | 简略描述 | ✅ 嵌在字段说明 + 功能逻辑中 |

**关键纪律**：FS 不重复 PRD 已说的业务背景；不重复 PRD 已描述的业务实体（FS 只补字段）。

## 业务术语 vs 技术术语

| 业务术语 | 技术术语（不在 FS §5 出现）|
|---|---|
| "将状态由'已发布'改为'已停用'" | `UPDATE quotation_template SET status = 'Deprecated'` |
| "模板名称在租户内唯一" | `UNIQUE INDEX UK_qt_tenant_name (tenant_id, name)` |
| "将订单占用金额累加上本单金额" | `OPEN_SO_AMOUNT += order_amount` |

**字段名英文**可在括号附带（如"状态（status）"），但**赋值表达式、SQL 关键字、运算符**不进入 §5 业务规则列。

## 何时拆子 FS

默认"一个或一组紧密相关的功能点 = 一份 FS"。建议拆分的触发条件：

- 某 FR 引入**独立的状态机**（如版本快照状态机独立于父对象生命周期）
- 某 FR 引入**独立的 API 子域**或独立的前后端组件
- 某 FR 是 P2（本期不实现）且需要 schema 预留 → 可在主 FS 中预留即可，不必单独成 FS

**经验法则**：5~10 个 FR 拆 1 份 FS 比较合理。20+ FR 一份 FS 太厚；1 FR 一份 FS 太碎。

## 数据表的通用约定

绝大多数 B2B 业务表含以下通用字段，可在 §6 通用约定中统一声明、表内省略：

- `tenant_id`（CHAR 20）— 多租户隔离
- 审计四件套：`create_time` / `create_user` / `update_time` / `update_user`
- 主键 `id`（CHAR 20）— 系统生成（雪花/UUID）

每张表只列与本业务相关的字段，避免噪声。

## 常见的字段命名约定

| 中文 | 英文 |
|---|---|
| 编号 / ID | `id`、`<entity>_id` |
| 名称 | `name` |
| 状态 | `status` |
| 类型 | `type`、`<entity>_type` |
| 是否启用 / 隐藏 / 必填 | `is_enabled` / `is_hidden` / `is_required` |
| 创建时间 / 创建人 | `create_time` / `create_user` |
| 更新时间 / 更新人 | `update_time` / `update_user` |
| 备注 | `remark` / `description` |
| 排序顺序 | `sort_order` |
| 父对象 ID | `parent_id`、`<parent_entity>_id` |
| 关联快照 | `snapshot` |

英文命名遵循 snake_case，业务命名遵循中文。
