# fs-writer

把 PRD 的功能点翻译成无歧义、可执行的 FS。每份 FS 服务于一个功能点（或一组紧密相关的功能点）。

## 起草前必读

每次起草前**必须**先读 `memory/lessons.md`，让历史教训指导本次撰写。

## 文件导航（按需加载）

| 文件 | 何时读 |
|---|---|
| `memory/lessons.md` | **每次起草前必读**：常见错误自检 + 业务规则写作规范 + 高价值机制 |
| `context/glossary.md` | 遇到术语歧义（数据类型、触发类型、字段表列定义等）时按需读 |
| `context/business-background.md` | PRD 不足、需要补充 FS 受众与边界常识时按需读 |
| `assets/fs-template.md` | 起草时复制此模板填空；含**决策表 / 分支流程图 / 异常清单 / 算法说明 4 种复杂逻辑表达手段**的骨架示例 |
| `assets/example/srm-quotation-snippet.md` | 不确定输出格式时参考典型 FS 片段 |
| `assets/example/credit-check-decision.md` | 复杂逻辑（决策表 + 异常清单）的实际产出形态参考 |

## PRD 与 FS 的关系

PRD 描述模块的业务流、需求与实体关系，识别出**功能点列表**。功能点是 PRD → FS 的桥梁。

- 一个功能点 = 一份 FS（默认）
- 一组紧密相关的功能点也可合并为一份 FS

## FS 6 节模板

按以下顺序写。每节写完邀请用户审阅或调整，不要一次写完全部。

### 1. 流程说明
- Mermaid flowchart 画业务流程
- 多流程则多图

### 2. 功能概述
固定元数据表：功能菜单 / 功能编号 / 所属模块 / 对应流程编号 / 功能类型 / 功能描述 / 前置条件 / 交互系统 / 后置条件 / 关联功能

功能编号格式：`FS_<模块>_M<NNN>`（如 `FS_SRM_M001`）

### 3. 功能界面
- 主界面 + 子界面（弹窗/对话框），各自一节
- **每个界面默认含 ASCII 简单原型示意图**

### 4. 关键字段说明
字段名**中英双写**，数据类型用业务类型枚举：

| 字段分组 | 字段名称（中文）| 字段名称（英文）| 数据类型 | 长度 | 必填 | 取值逻辑 |
|---|---|---|---|---|---|---|

**数据类型枚举**：CHAR / NUM / DATE / DATETIME / ACL / 勾选框 / JSON（详见 `context/glossary.md`）

**枚举值独立成表**（强约束）：≥3 个固定选项必须在 §4 末尾追加"枚举值定义"小节，独立列表。

### 5. 功能逻辑
两层结构：

**5.1 关键项说明**：功能按钮、关联数据、重点逻辑（3~5 条总结）

**5.2 详细功能逻辑**（按动作分组）：

```
#### 动作名称（如"新增 XX"）

> **所属模块**：<模块名>
> **触发按钮**：<具体按钮名>
> **操作对象**：<被操作的对象>
> **前置条件**：<可选>

| 执行步骤 | 执行步骤描述 | 标准业务规则 |
|---|---|---|
| 1 | 用户做什么 | 完整中文句，必要时括号附带英文字段名 |
```

**触发类型必标其一**：用户操作 / 系统自动 / 被调用 / 定时任务（详见 `context/glossary.md`）

**"标准业务规则"列写作规范**：必须是完整的中文句子，写业务因果与约束，不写 SQL/赋值。详见 `memory/lessons.md`。

**复杂动作**（3+ 条件分支、异常路径、循环重试）：追加决策表 / 分支流程图 / 异常清单 / 算法说明。**4 种工具的骨架示例已内置在 `assets/fs-template.md`**，按需复制使用。

| 动作复杂度 | 推荐手段 |
|---|---|
| 简单线性 CRUD | 仅步骤表 |
| 1~2 个判断 | 步骤表（判断写在"标准业务规则"列里）|
| 3+ 条件组合 | 步骤表 + 决策表 |
| 含分叉与异常路径 | 步骤表 + 分支流程图 |
| 需完整覆盖异常 | 步骤表 + 异常清单表 |
| 含循环/重试/算法 | 步骤表 + 算法说明 |

### 6. 数据表结构

每张表一节，字段中英双写，数据类型与 §4 对齐：

```
#### 主表：<中文表名> (`<table_name>`)

> **所属模块**：<模块名>
> **表单名称**：<表单名>
> **表单类型**：新增配置表 / 新增枚举表 / 新增子表单 / 已有表单加字段

| 序号 | 字段ID（英文）| 字段名称（中文）| 数据类型 | 长度 | 必填 | 描述 |
```

## 工作流（分段渐进式）

### Step 0 — 确认范围
读 PRD 文件 / 用户描述的功能点。用一句话回应"本次 FS 覆盖：<功能点列表>"，等用户确认。

### Step 1 — 写 §1 ~ §3（前半段·流程界面）
按顺序写完 §1 流程说明、§2 功能概述、§3 功能界面。一起交付审阅。

### Step 2 — 写 §4 ~ §6（后半段·逻辑数据）
审阅通过后写完 §4 关键字段说明、§5 功能逻辑、§6 数据表结构。一起交付。

### Step 3 — 询问是否追加 §7 API / §8 测试用例（默认不追加）

使用 `AskUserQuestion` 询问。三个选项：
- 都不追加（推荐）— FS 到 §6 数据表结束
- 追加 §7 API 设计
- 追加 §8 测试用例

默认推荐"都不追加"。多数前后端一体化项目到 §6 已经够用了。

## 修订模式

目标 FS 文件已存在时，问用户：
1. 改某节内容（指定节号）
2. 加新功能点（追加 SR）
3. PRD 已更新，同步差异
4. 仅润色不改行为（版本号 PATCH）

修订完成后更新文件末尾的 CHANGELOG。**重要修订经验请记录到 `memory/lessons.md`**。

## 不写什么

- **不默认写"错误码"独立章节** — 错误提示文案直接放 §5 步骤表的"标准业务规则"列
- **不默认写"API 接口"章节** — 仅 Step 3 用户主动追加才写
- **不默认写"Test Case"章节** — 仅 Step 3 用户主动追加才写
- **不画 ER 图** — 数据表结构本身已表达
- **不臆造** — PRD 未明确的逻辑，缺信息时标"[待确认]"
