# fs-writer

把 PRD 的功能点翻译成无歧义、可执行的 FS。每份 FS 服务于一个功能点（或一组紧密相关的功能点）。

## PRD 与 FS 的关系

PRD 描述模块的业务流、需求与实体关系，识别出**功能点列表**。功能点是 PRD → FS 的桥梁。

- 一个功能点 = 一份 FS（默认）
- 一组紧密相关的功能点也可合并为一份 FS

## FS 模板（6 节）

按以下顺序写。每节写完邀请用户审阅或调整，不要一次写完全部。

### 1. 流程说明
- 用 **Mermaid flowchart** 画出功能涉及的业务流程
- 若功能涉及多个流程，画多张图（如"新增流程"、"编辑流程"、"删除流程"）
- 节点为业务动作（不是系统组件），含决策菱形与分支

### 2. 功能概述
固定元数据表，字段如下：

| 字段 | 内容 |
|---|---|
| 功能菜单 | 用户在系统里看到的菜单名 |
| 功能编号 | FS_<模块>_M<NNN>（如 FS_WAREHOUSE_M007）|
| 所属模块 | 【一级模块】-【二级模块】|
| 对应流程编号 | 如 1.7-0 |
| 功能类型 | ☑ 功能 / □ 报表 / □ 接口（三选一打勾） |
| 功能描述 | 1~5 条要点列举本功能做什么 |
| 前置条件 | 1~N 条 |
| 交互系统 | 与外部/其他模块的交互点（如有）|
| 后置条件 | 1~N 条 |
| 关联功能 | 上下游或相关功能点引用 |

### 3. 功能界面
- 主界面：列出页面元素（标题区/工具栏/筛选区/数据表格/分页等）+ **ASCII 简单原型示意图**
- 子界面：弹窗、对话框各自一节，列出表单字段、操作按钮等 + **ASCII 简单原型示意图**
- ASCII 原型只画结构骨架（页面分区、按钮位置、表格列），不画像素级细节

### 4. 关键字段说明

统一表格格式（**中英双写**，便于业务可读 + 开发精确）：

| 字段分组 | 字段名称（中文）| 字段名称（英文）| 数据类型 | 长度 | 必填 | 取值逻辑 |
|---|---|---|---|---|---|---|

**数据类型枚举**（业务类型，非具体 SQL 方言）：

| 数据类型 | 含义 | 示例 |
|---|---|---|
| CHAR | 文本 | 编码、名称、描述 |
| NUM | 数字 | 金额、数量、百分比 |
| DATE | 日期 | 有效期至、创建日期 |
| DATETIME | 日期时间 | 创建时间、更新时间 |
| ACL | 下拉选择（引用其他表）| 公司代码、货币、风险类别 |
| 勾选框 | 是/否开关 | 是否冻结、是否启用 |
| JSON | 复杂结构 | 配置快照、扩展属性 |

**取值逻辑写法**：

- 手工输入 / 系统生成（按规则）/ 系统显示（取上下文）
- ACL 类型必写"参考【表名】"格式（如"参考【信贷组配置表】"）

**枚举值独立成表**（强约束）：

若字段有 **≥3 个固定选项**，**必须**在 §4 末尾追加"枚举值定义"小节，独立列表。
- 取值逻辑列写"参考【XX 配置表】"
- 不允许把枚举值直接写在取值逻辑列中

枚举值定义表格式：

| 枚举表名称 | 编码 | 名称 |
|---|---|---|
| 信贷组配置 | 01 | 销售订单信贷组 |
| 信贷组配置 | 02 | 交货信贷组 |

### 5. 功能逻辑
两层结构：

**5.1 关键项说明**（简短列出）：
- 功能按钮（新增/编辑/删除/打印/刷新 等）
- 关联数据
- 重点逻辑（3~5 条总结性陈述）

**5.2 详细功能逻辑**（按动作分组，每个动作一张表 + 固定头部）：

```
#### 动作名称（如"新增 XX"）

> **所属模块**：<模块名>
> **触发按钮**：<具体按钮名，如"提交"、"删除"、"过账"；若非按钮触发则写定时任务名/事件名>
> **操作对象**：<被操作的表单/对象>
> **前置条件**：<可选；如有前置才写>

| 执行步骤 | 执行步骤描述 | 标准业务规则 |
|---|---|---|
| 1 | 用户做什么 | 系统应当怎样判断/处理（**含字段更新说明**：如"未清销售订单占用 += 金额"）|
| 2 | ... | ... |
```

**关键约束**：
- **一个按钮一个段落**：不同按钮（提交、删除、关闭、过账）不能写在同一段
- **不同表单对象一个段落**：销售订单 / 交货单 / 发票各自独立
- **触发按钮必须写清楚**：用户感知的按钮名（如"确认发布"、"停用"），不写抽象动词（如"提交"过于泛化时要具化）
- **"标准业务规则"列必须是完整的中文句子**：写业务因果与约束，不写 SQL/赋值表达式。详见下方"标准业务规则列写作规范"

**"标准业务规则"列写作规范**：

| 维度 | 要求 | ❌ 错误示例 | ✅ 正确示例 |
|---|---|---|---|
| 句子完整性 | 完整的中文句子（有主谓宾） | `quotation_template.status = 'Deprecated'；deprecated_at = NOW()` | 将模板状态由"已发布"改为"已停用"，并记录停用时间为当前系统时间 |
| 词汇 | 中文业务术语为主 | `effective_from` / `status` / `ref_count` | 启用日期 / 状态 / 引用次数 |
| 枚举值 | 用业务值（中文）| `'Published'` / `'Active'` | "已发布" / "已生效" |
| 必要英文 | 必要时在括号里附带英文名（便于开发对照）| 全部中文，开发不知道改哪个字段 | 将模板状态（status）由"已发布"改为"已停用" |
| 表达 | 写因果与约束 | "状态改为已停用" | "将状态由已发布改为已停用；此操作不可逆，停用后不能再回到已发布状态" |
| 字段更新 | 用动词描述，不用赋值符号 | `未清销售订单占用 += 金额` | 将业务伙伴信用视图的"未清销售订单占用"金额累加上本订单金额 |
| 错误提示 | 原文照搬完整文案 | "提示错误" | 提示："模板名称已存在，请改用其他名称" |

涵盖的触发类型（每个动作必标其一）：
- 用户操作触发（最多见，标"触发按钮：XX"）
- 系统自动触发（如状态机自动流转，标"触发：系统自动 - XX 事件"）
- 其他流程调用（如被上游事件触发，标"触发：被调用 - XX 上游事件"）
- 定时任务触发（标"触发：定时任务 - XX，频率：XX"）

四类触发都要覆盖到。若某类不适用本功能，跳过。

### 5.3 复杂逻辑表达手段（按需选用）

步骤表是默认主表达方式，但遇到复杂逻辑时单靠步骤表会力不从心（条件分支多、异常路径复杂、含循环/重试/状态迁移）。此时**在该动作的步骤表后追加子节**，使用以下表达手段之一或组合。**不强制每个动作都用，按复杂度按需选择**：

| 动作复杂度 | 推荐手段 |
|---|---|
| 简单线性（CRUD）| 仅步骤表 |
| 含 1~2 个判断 | 步骤表（判断写在某步骤的"标准业务规则"列里）|
| 含 3+ 条件组合 | 步骤表 + **决策表** |
| 含分叉与异常路径 | 步骤表 + **分支流程图（Mermaid flowchart）** |
| 需完整覆盖异常 | 步骤表 + **异常清单表** |
| 含循环/重试/算法 | 步骤表 + **算法说明**（伪代码或编号文字）|

#### 手段 A：决策表（多条件分支）

适用：多个条件按"是/否"组合产生不同结果（典型 if/elif/else 矩阵）。

```
**决策表：<场景名>**

| 条件 \ 规则编号 | R1 | R2 | R3 | R4 |
|---|---|---|---|---|
| <条件 1>？ | 是 | 是 | 否 | 否 |
| <条件 2>？ | 否 | 是 | 否 | 是 |
| <条件 3>？ | - | - | - | 是 |
| **→ 系统动作** | <动作 1> | <动作 2> | <动作 3> | <动作 4> |
```

要求：
- 条件必须用问句形式（"是否充足？"），便于按"是/否"判断
- 规则列必须 MECE（所有可能的组合都被覆盖，不重叠不遗漏）
- "-"表示该规则下此条件不参与判断（don't care）
- 每条规则下方建议括号附测试用例编号（如 R1 → TC-001-01），便于 §8 测试用例追溯

#### 手段 B：分支流程图（Mermaid flowchart）

适用：主流程含多个决策菱形 + 异常路径 + 循环重试。

```
**分支流程图：<场景名>**

\`\`\`mermaid
flowchart TD
    Start[起点] --> Action1[动作]
    Action1 --> Decision{决策点?}
    Decision -->|条件 A| ActionA[动作 A]
    Decision -->|条件 B| ActionB[动作 B]
    ActionA --> Retry{重试条件?}
    Retry -->|是| Action1
    Retry -->|否| Alert[告警]
\`\`\`
```

要求：
- 决策菱形用问句（"乐观锁是否冲突？"）
- 异常路径与主路径视觉对等，不要把异常隐藏在主路径下方
- 循环、重试、降级路径要显式画出

#### 手段 C：异常清单表

适用：需要完整覆盖某动作的全部异常分支。

```
**异常清单：<动作名>**

| 异常场景 | 触发条件 | 系统响应 | 用户感知 | 是否阻断 |
|---|---|---|---|---|
| <场景名> | <什么情况下触发> | <系统怎样处理> | <用户看到什么> | 是 / 否 |
```

要求：
- 异常场景必须有明确名称，便于在错误码表（§7）中追溯
- "是否阻断"区分硬错误（拦截后续）与软警告（继续但提示）
- 异常清单完整后，§7 错误码表可由本表逐行派生

#### 手段 D：算法说明（伪代码或编号文字）

适用：含循环、批处理、重试、复杂状态迁移、聚合/计算公式的场景。

```
**算法说明：<算法名>**

1. 初始化：<初始状态、计数器、缓冲区>
2. 主循环：
   2.1 取出下一批数据（每批 N 条）
   2.2 对每条数据：
       a. 执行业务校验
       b. 若失败，进入重试队列（最多 3 次）
       c. 若成功，写入结果
   2.3 提交本批事务
3. 退出条件：所有数据处理完毕 或 失败累计超阈值
4. 错误处理：见异常清单（手段 C）
```

要求：
- 编号清晰，便于开发对照实现
- 复杂条件用业务语言（"失败累计超阈值"），不用代码语法（`if failed > threshold`）
- 关键参数（批次大小、重试次数、阈值）显式给出，便于配置化

### 5.4 关于"按需选用"的判断指引

- 写完步骤表后自问：**业务人员/QA 看完能不能正确理解所有分支与异常**？若不能，加补充表达
- 如果只是 1~2 个判断，直接写在"标准业务规则"列里，**不要为了形式而引入决策表**
- 如果某个动作要用 3 个以上手段，考虑这个动作是不是太复杂、需要拆成多个动作

### 6. 数据表结构

每张表一节，统一格式（**中英字段名双列**，数据类型与 §4 关键字段说明对齐）：

```
#### 主表：<中文表名> (`<table_name>`)
| 序号 | 字段ID（英文）| 字段名称（中文）| 数据类型 | 长度 | 必填 | 描述 |
|---|---|---|---|---|---|---|
| 1 | id | 主键 | CHAR | 20 | 是 | 主键 |
```

**数据类型**：使用 §4 同一枚举（CHAR / NUM / DATE / DATETIME / ACL / 勾选框 / JSON）。

**主表结构表后追加**：
- 索引说明（含名称、字段顺序、用途）
- 关键约束（外键、唯一约束、check 约束）
- 表单类型标注：在表名上方注明 `表单类型：新增配置表 / 新增枚举表 / 新增子表单 / 已有表单加字段`（参考 DxERP 指南规范，便于 AI 区分新表还是旧表加字段）

**表单归属标注**：表名上方注明 `所属模块：<模块名> | 表单名称：<表单名>`，避免 AI 需要额外查询归属。

## 工作流（分段渐进式）

### Step 0 — 确认范围
读 PRD 文件 / 用户描述的功能点。用一句话回应"本次 FS 覆盖：<功能点列表>"，等用户确认。

### Step 1 — 写 §1 ~ §3（前半段·流程界面）
按顺序写完 §1 流程说明、§2 功能概述、§3 功能界面。一起交付审阅。

### Step 2 — 写 §4 ~ §6（后半段·逻辑数据）
审阅通过后写完 §4 关键字段说明、§5 功能逻辑、§6 数据表结构。一起交付。

### Step 3 — 询问是否追加 API 设计与测试用例（关键决策点）

§4 ~ §6 交付完成后，使用 `AskUserQuestion` 询问用户是否要追加可选章节。**默认不追加**——多数前后端一体化项目到 §6 已经够用了。

```yaml
question: "FS 主体（§1~§6）已完成。是否需要追加 API 设计与测试用例章节？"
header: "可选章节"
multiSelect: true
options:
  - label: "都不追加（推荐）"
    description: "FS 到 §6 数据表结构结束。适合前后端一体化项目；测试用例由专门文档承载"
  - label: "追加 §7 API 设计"
    description: "适合跨服务对接、对外开放 API、或团队习惯写 HTTP 契约的项目"
  - label: "追加 §8 测试用例"
    description: "FS 内联 Test Case；适合没有独立测试用例库的小项目"
```

根据用户回答执行：
- 选"都不追加" → FS 完成，停在 §6 之后，输出文件路径与 CHANGELOG 提示，结束
- 选"追加 §7 API 设计" → 写 §7（hook/action 列表为主；跨服务边界才写 HTTP 路由）
- 选"追加 §8 测试用例" → 写 §8（按 §5 中的动作展开，每动作 1 happy path + N 边缘案例，Given-When-Then 格式）

**不要主动询问其他可选章节**（如错误码、ER 图、NFR），这些默认不写。用户特别要求时再加。

## 写作要求

- **短**：每节用最少篇幅讲清楚；不写"设计决策记录""anti-pattern""为什么这样设计"等元说明
- **精确**：字段名中英双写，让业务可读 + 开发精确；数据类型用业务类型枚举（CHAR/NUM/DATE/ACL/勾选框/JSON）
- **触发标注必明确**：§5 详细功能逻辑必须覆盖四类触发（用户/系统自动/被调用/定时）；定时任务漏掉是最常见错误
- **按钮名必须具化**：§5 写"触发按钮：提交"时确认是否本功能确有"提交"按钮，避免抽象动词
- **枚举值独立成表**：≥3 个固定选项的字段，必须独立成枚举表；不允许内嵌在取值逻辑列中
- **一个按钮一个段落**：不同按钮 / 不同操作对象 = 不同段落，不能混在一起
- **状态信息嵌在字段说明 + 功能逻辑中**：状态机不独立成章；status 字段的取值在 §4 字段说明的"取值逻辑"或独立枚举表中；状态流转规则在 §5 功能逻辑中描述
- **PRD 来源可选标注**：若 PRD 有明确 BR 编号，§5 步骤表可加一列"PRD 来源"；若 PRD 是散文描述，则不强制标注

## 常见错误（自检清单）

| 错误 | 问题 | 正确做法 |
|---|---|---|
| 在"原有表单新增字段"中写"新增 XX 子表单" | AI 无法区分新表还是旧表加字段 | 新增表单独立一张表格，标注"表单类型：新增子表单" |
| 枚举值写在取值逻辑列中 | AI 漏掉需要新增枚举配置表 | 枚举值独立成表，取值逻辑写"参考【XX 配置表】" |
| 多个按钮操作写在同一段 | AI 无法准确拆分独立流程 | 每个按钮操作独立一段，标注触发按钮名称 |
| 不标注所属模块 | AI 需要额外查询确定归属 | 每张表格上方标注所属模块 + 表单名称 |
| 抽象触发词（如"用户触发"）| 无法对应到具体 UI 按钮 | 用具体按钮名（"提交"、"过账"、"确认发布"）|

## 不写什么

- **不默认写"错误码"独立章节** — 错误提示文案直接放 §5 步骤表的"标准业务规则"列
- **不默认写"API 接口"章节** — 仅当 Step 3 用户选了"追加 §7 API 设计"才写
- **不默认写"Test Case"章节** — 仅当 Step 3 用户选了"追加 §8 测试用例"才写
- **不画 ER 图** — 数据表结构本身已表达；若关系复杂可在 §6 开头加一两句关系说明
- **不臆造** — PRD 未明确的逻辑，缺信息时标"[待确认]"

## 修订模式

目标 FS 已存在时，问用户：
1. 改某节内容（指定节号）
2. 加新动作 / 新字段
3. PRD 已更新，同步差异

修订后在文件末尾追加 CHANGELOG。
