# architect-reviewer 长期教训库

本文件存放架构师 review 实战中沉淀的经验与常见自检规则。

**范围界定**：
- ✅ 跨次 review 反复有效的发现模式、必查清单
- ❌ 不放版本号修订日志（归仓库根 CHANGELOG）

---

## Review 必查清单（每次 review 前过一遍）

### 技术可行性层
- [ ] §5 每个 FR 是否暗示了"现有技术栈做不了"的需求？
- [ ] AI 相关 FR 是否在已有 AI 中台能力范围内？
- [ ] 是否有"全表实时聚合 + 高并发 + 大数据量"这类违反基础原则的需求？

### 平台兼容性层
- [ ] PRD 是否暗示绕过平台统一组件（通知 / IAM / 审计）？
- [ ] 跨模块集成点是否清晰识别？
- [ ] 与现有架构假设是否冲突？

### 数据模型层
- [ ] §4 业务实体是否完整？审计 / 版本 / 关联表是否漏？
- [ ] 实体关系基数是否合理？没有过度多对多？
- [ ] 是否暗示了超大表 / 超深嵌套 / 跨租户大数据扫描？

### 性能扩展层
- [ ] FR 中是否有"全量列表 + 实时聚合 + 不分页"这类性能炸弹？
- [ ] 高并发场景是否被识别？
- [ ] 数据量级估算是否合理？

### 演进性层
- [ ] P2 FR 是否显式标注 schema 预留要求？
- [ ] §6.3 未来扩展是否在本期架构中预留落地点？
- [ ] 是否过度耦合于某客户的次性需求？

## 高价值机制

### 1. "实时" 字眼必追问

PRD 里出现"实时"二字，必须追问具体的 P95 时延要求（<1秒？<10秒？<1分钟？）。
不同的"实时"含义对应完全不同的架构（同步 vs 准实时 vs 异步），不澄清就进 FS 必踩坑。

### 2. "全部 / 所有 / 永久" 字眼必追问

PRD 里出现"展示全部历史"、"永久保留"、"所有数据可查"等，必须追问：
- 数据量级（千 / 万 / 百万 / 十亿）
- 保留期（具体年限）
- 查询频率（高频 / 低频）

往往会发现真实需求是"近 N 个月"或"按需查询"，而非字面意义的"全部"。

### 3. "AI 智能" 字眼必拆解

PRD 里出现"AI 智能推荐 / 智能预测"等，必须拆解：
- 输入数据从哪来？
- 训练数据是否足够？
- 是辅助决策还是替代人工？
- 失败 / 异常时降级到什么？

否则进 FS 阶段会出现"AI 黑盒 + 无降级 + 无解释"的问题。

### 4. P2 FR 的 schema 预留检查

如果 PRD 含 P2 FR（本期不实现），架构师必查：
- 该 FR 未来上线需要什么字段？
- 当前 PRD 的 §4 业务实体是否预留了相关概念？
- FS 起草时是否需要在 schema 中加扩展位（如 `formula` / `is_anomaly`）？

未预留 → 未来上线时破坏性迁移成本高。

### 5. 跨模块集成必明确

PRD 涉及跨模块时（如本模块发布事件，被其他模块订阅），架构师必反馈：
- 是同步 RPC 还是异步事件？
- 失败如何处理？
- 上下游谁发布契约？

## 常见反馈措辞模板

### ⚠️ 建议类
> "§5 FR-X.Y 提到'实时同步'，建议澄清 P95 时延要求与失败重试策略。"
> "§6.3 未来扩展的 F-N 能力，建议本期 PRD 在 §4 业务实体处预留对应概念。"

### ❌ 必改类
> "§5 FR-X.Y 要求'展示全部供应商的全部历史报价'，在租户内供应商 ≥ 1000 + 历史报价 ≥ 10 万时无法实时聚合，需澄清是否分页 / 是否限范围。"
> "§5 FR-X.Y 要求'通过自定义渠道发通知'，违反平台统一通知组件规范，请改为'通过平台标准通知组件分发'。"

### ✅ 通过类
> "§4 业务实体清单与 §5 FR 引用一致，且预留了版本快照实体，演进性良好。"

## 不该评的（避免越权）

- ❌ 业务价值 / 用户痛点 → BA 的事
- ❌ 测试用例可行性 → QA 的事
- ❌ 具体技术选型（PostgreSQL / Redis / React 等）→ 技术设计层的事
- ❌ 字段名 / 类型 → FS 层的事
