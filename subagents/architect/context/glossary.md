# 架构师术语与常见陷阱

## Architect 关心的核心概念

| 术语 | 含义 |
|---|---|
| **技术可行性** | 当前技术栈能否实现此 FR；时间 / 成本 / 复杂度评估 |
| **平台兼容性** | 新需求是否与现有平台架构假设冲突 |
| **数据建模深度** | PRD 层的实体抽象是否合理（不写字段但实体结构要对）|
| **状态机一致性** | 跨实体的状态流转是否冲突 |
| **演进性** | 当前设计是否支持未来扩展，避免破坏性迁移 |

## 常见 PRD 架构侧陷阱

| 陷阱 | 典型表现 | 反馈建议 |
|---|---|---|
| 实时性要求过高 | "用户操作秒级感知"+"涉及多源数据" | 反馈：澄清"实时"的具体 P95 时延要求；评估是否需异步 |
| 与现有约束冲突 | PRD 要求"自定义通知渠道" 但平台规范要求统一通知组件 | 反馈：要求遵循平台统一约束 |
| 隐含超大表 | "保存所有历史操作 + 永久不删除 + 跨租户" | 反馈：要求明确数据保留期、分区策略 |
| 状态机冲突 | 实体 A 引用实体 B，但两者状态机不一致 | 反馈：要求明确跨实体状态联动规则 |
| 演进性差 | P2 FR 完全没在 PRD 提及 schema 扩展点 | 反馈：要求 P2 FR 显式标注"未来 schema 预留"|

## 反例：不应越界的内容

- ❌ "建议用 PostgreSQL 而不是 MySQL" → 具体选型属技术设计层
- ❌ "应该用 Redis 做缓存" → 同上
- ❌ "前端用 React" → 同上
- ✅ "需要预留缓存层（具体技术由后续设计决定）"
- ✅ "建议采用事件驱动而非同步调用，以避免性能耦合"
