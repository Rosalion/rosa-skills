# qa-reviewer 长期教训库

本文件存放 QA review 实战中沉淀的经验与常见自检规则。

**范围界定**：
- ✅ 跨次 review 反复有效的发现模式、必查清单
- ❌ 不放版本号修订日志（归仓库根 CHANGELOG）

---

## Review 必查清单（每次 review 前过一遍）

### 可测性层
- [ ] 每条 FR 都有验收标准吗？
- [ ] 验收标准是否用 Given-When-Then 格式？
- [ ] X / Y / Z 是否能转化为具体可执行的测试步骤？
- [ ] 有没有"系统应正确处理 / 合理响应"这类模糊表达？

### 边界层
- [ ] 空值 / 最大长度 / 极值边界是否被讨论？
- [ ] 时间边界（截止时刻、跨日 / 跨月 / 跨年）是否被讨论？
- [ ] 数字精度 / 浮点边界是否被讨论（金额、数量场景）？

### 异常分支层
- [ ] 每个用户动作的"失败 / 拒绝"路径是否描述？
- [ ] 跨模块依赖失败时的降级是否明确？
- [ ] 权限不足 / 跨租户访问的拒绝行为是否描述？

### 状态机层
- [ ] 每条状态转换是否都有对应的验收标准？
- [ ] 非法转换的拒绝行为是否覆盖？
- [ ] 并发场景（乐观锁）是否被讨论？

### 跨 FR 一致性层
- [ ] 多个 FR 之间业务规则是否冲突？
- [ ] 同一业务场景在不同 FR 中描述是否一致？

## 高价值机制

### 1. "正确 / 合理 / 适当" 字眼必追问

PRD 里出现"系统应正确处理 / 合理响应 / 适当显示"等模糊表达，**必出 ❌ 必改**：
要求改写为具体的 Given-When-Then，含可观察的"则 Z"。

### 2. "只看主流程" 识别

如果某 FR 的验收标准只描述了 happy path 而没有失败路径，**至少出 ⚠️ 建议**：
补充至少 1 条"给定 X，当 Y 错误条件，则 Z 拒绝/降级响应"。

### 3. "数字 / 金额 / 数量" FR 必查边界

任何涉及数字的 FR，必查：
- 是否允许 0？
- 是否允许负数？
- 是否允许小数？精度多少位？
- 是否有上下限？
- 货币场景下的舍入规则？

### 4. "时间 / 日期" FR 必查边界

任何涉及时间的 FR，必查：
- 截止时刻是否含？（< vs ≤）
- 跨时区如何处理？
- 临界场景（截止前 1ms 提交）的处理？
- 时区切换、夏令时？

### 5. 跨 FR 冲突识别

PRD 内多个 FR 涉及同一业务对象时，必交叉对比业务规则。常见冲突：
- FR-A 说"允许 X 操作"，FR-B 说"在 Y 状态下不允许 X 操作"——这是冲突还是补充？
- FR-A 的验收标准与 FR-B 的业务规则相悖？

## 常见反馈措辞模板

### ⚠️ 建议类
> "§5 FR-X.Y 的验收标准仅描述了 happy path，建议补充至少 1 条失败路径的 Given-When-Then。"
> "§5 FR-X.Y 涉及金额，建议明确：是否允许 0 / 负数 / 小数位精度。"

### ❌ 必改类
> "§5 FR-X.Y 的验收标准'系统应正确显示数据'过于模糊，请改写为可执行的 Given-When-Then。"
> "§5 FR-X.Y 与 FR-Z.W 业务规则冲突：前者允许在草稿状态修改 X 字段，后者要求 X 字段始终不可改。请澄清。"

### ✅ 通过类
> "§5 FR-X.Y 验收标准覆盖了 3 条 Given-When-Then，分别覆盖 happy / 边界 / 失败路径，可测性良好。"

## 不该评的（避免越权）

- ❌ 用户价值 / 业务诉求 → BA 的事
- ❌ 技术实现复杂度 → architect 的事
- ❌ 写完整测试用例（QA reviewer 只指出"需要覆盖什么"，具体用例由专门 Test Case 文档承载）
- ❌ 性能指标具体数字 → architect 或 NFR 的事
