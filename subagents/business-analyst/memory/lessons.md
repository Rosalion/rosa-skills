# business-analyst-reviewer 长期教训库

本文件存放 BA review 实战中沉淀的经验与常见自检规则。

**范围界定**：
- ✅ 跨次 review 反复有效的发现模式、必查清单
- ❌ 不放版本号修订日志（归仓库根 CHANGELOG）

---

## Review 必查清单（每次 review 前过一遍）

### 用户价值层
- [ ] §1 摘要的"为谁解决什么问题"是否一句话说清楚？
- [ ] §2.2 目标用户的角色是否真实存在？还是 PM 臆造？
- [ ] 价值主张能否对应到具体的 KPI 改善？

### 业务流层
- [ ] §3 业务流程的每条路径是否走得通？没有断头？
- [ ] 决策菱形的所有分支都覆盖了吗？
- [ ] 跨角色 / 跨模块的移交点是否明确？

### 范围层
- [ ] §6.2 范围外是否至少 5 项且写了排除原因？
- [ ] §6.3 未来扩展里是否藏着"应该本期做"的能力？

### FR 覆盖层
- [ ] 业务流中每个关键动作都有对应的 FR 吗？
- [ ] 边界 FR（取消 / 撤回 / 权限不足）是否被遗漏？
- [ ] FR 优先级是否合理（不全是 P0）？

### 业务规则层
- [ ] 异常业务场景是否被讨论？
- [ ] 业务规则是否完整中文句、不缺主语谓语？

## 高价值机制

### 1. "5 项排除"硬性门槛

§6.2 范围外少于 5 项的 PRD 90% 会范围蔓延。如果不足 5 项，**必出 ❌ 必改反馈**：要求 PM 用 Scope Exclusion 追问法补全。

### 2. "脑补角色"快速识别

如果 §2.2 角色名是"运营人员"、"业务人员"这类**没有具体职责描述**的笼统称谓，往往是 PM 脑补。反馈：要求确认客户方实际存在此角色，并具化职责。

### 3. "断头流程"识别

§3 业务流程的 Mermaid 图里如果存在没有连到终点（`[*]` 或具体结束节点）的分支，即为断头流程。**这类问题必出 ❌ 必改**。

### 4. "P0 全占"识别

如果 §5 优先级汇总 P0 占比 ≥ 80%，本质是没有优先级。反馈：要求强制分级，根据"如果只能砍掉一半，哪些必须保留"的逻辑重排。

## 常见反馈措辞模板

### ⚠️ 建议类
> "§5 FR-X.Y 缺少边界场景的处理（如 [具体场景]），建议补充业务规则。"
> "§6.1 范围内列出了 [N] 项能力，建议核实是否在本期合理交付能力内。"

### ❌ 必改类
> "§3 业务流程图的 [节点 A → 节点 B] 路径未画出错误分支，存在死循环风险。"
> "§5 FR-X.Y 的业务规则与 §3 流程图描述的步骤不一致，需要对齐。"

### ✅ 通过类
> "§4 业务实体清单与 §3 业务流程引用的对象一致，无遗漏。"

## 不该评的（避免越权）

- ❌ 技术实现复杂度 → architect 的事
- ❌ 测试用例可行性 → qa 的事
- ❌ 字段命名规范 → 不在 PRD 层级
- ❌ 性能指标合理性 → architect 的事
